# QA Automation Architecture

## Overview

This folder contains a JavaScript Playwright Test suite for browser and API validation of the Insurance Claims Management application. It is a separate test package: it exercises the existing application through its UI and HTTP APIs without relocating or replacing application source, component tests, backend tests, or API contracts.

The application architecture and service responsibilities are documented in the repository-level [ARCHITECTURE.md](../ARCHITECTURE.md). This page describes how the QA automation is organized and how its tests exercise that application.

## Test execution flow

```text
                         qa-automation/
┌───────────────────────────────────────────────────────────────┐
│ Playwright Test runner                                        │
│ playwright.config.js: Chromium, base URL, workers, reporting  │
│                                                               │
│ tests/*.spec.js ──► fixtures/test.js ──► page objects         │
│   auth                 LoginPage             login.page.js     │
│   claim wizard         ClaimPage             claim.page.js     │
│   admin workflow       AdminClaimsPage       admin-claims.page.js
│   API authorization   Playwright request                         │
│                                                               │
│ data/users.js     data/claims.js     test-results/             │
└───────────┬───────────────────┬───────────────────────────────┘
            │ Browser UI       │ HTTP API
            ▼                  ▼
       Next.js UI :3001 ─────► BFF :8090 ─────► Claims Service :8080
                                  │                    │
                                  └── Keycloak :8180   └── PostgreSQL
```

The browser tests use the Next.js application and follow its real login, claim-submission, and admin-review flows. The API authorization tests send anonymous requests to the BFF. This suite does not mock application responses or start the application servers itself; the local application stack must be running before those tests execute.

## Project layout

```text
qa-automation/
  playwright.config.js       Playwright discovery, browser, timeouts, reporting
  package.json               Test commands and Playwright dependency
  fixtures/
    test.js                  Shared Playwright fixtures and page-object creation
  pages/
    login.page.js            Login-page actions and readiness check
    claim.page.js            Claim wizard and claimant claim-list actions
    admin-claims.page.js     Admin filtering and claim-status actions
  data/
    users.js                 Environment-overridable demo account data
    claims.js                Unique claim data created for each lifecycle test
  tests/
    auth.spec.js             Authentication and role-routing cases
    api.spec.js              Anonymous API authorization cases
    claim-wizard.spec.js     Required-field validation case
    role-access-negative.spec.js
                 Claimant route denial and admin status-option checks
    admin-claims.spec.js     Admin review and approval workflow
    claimant-admin-e2e.spec.js
                             Claimant-to-admin end-to-end workflow
  docs/
    TEST-CASES.md            Scenario IDs, priorities, and traceability
  tescases.md                Detailed steps, test types, and defect references
  evidence/                  Screenshots attached to manually reproduced defects
  test-results/              Failure artifacts generated by Playwright
  playwright-report/         HTML report generated by Playwright
```

`test-results/` and `playwright-report/` are generated output folders. Their contents are not required as test source. The directory layout keeps test cases separate from reusable browser interactions, fixtures, and data.

## Test responsibilities

| Test file | Coverage |
|---|---|
| `tests/auth.spec.js` | Login page, invalid credentials, claimant routing, and admin routing |
| `tests/api.spec.js` | Anonymous access is rejected by claimant and admin claims endpoints |
| `tests/claim-wizard.spec.js` | Required incident fields prevent advancing an empty claim |
| `tests/role-access-negative.spec.js` | Claimant is denied the admin route; approved claim cannot return to earlier statuses |
| `tests/admin-claims.spec.js` | Creates a claim, then exercises admin review and approval |
| `tests/claimant-admin-e2e.spec.js` | Claimant submits a claim, then an admin reviews and approves it |

The current specs define 11 Playwright cases. The traceability matrix is maintained in [docs/TEST-CASES.md](docs/TEST-CASES.md), with detailed steps and manual defect references in [tescases.md](tescases.md). Screenshots of five manually reproduced UI defects are linked from [DEFECTS.md](DEFECTS.md) and stored under `evidence/`; they are not Playwright failure artifacts.

## Shared test design

- **Fixtures:** `fixtures/test.js` extends Playwright's `test` with a page object per browser test. Each test receives its own isolated Playwright `page`.
- **Page objects:** `pages/` holds reusable user actions and UI synchronization. Assertions are based on visible controls, accessible roles, test IDs, and route changes rather than fixed sleeps.
- **Test data:** `data/claims.js` generates a unique claim description and recent incident date for each lifecycle test. Claim IDs are read back from the claimant's claims table rather than hardcoded.
- **Credentials:** `data/users.js` reads `CLAIMANT_EMAIL`, `CLAIMANT_PASSWORD`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD`, with local demo defaults. Playwright does not load `.env` automatically; set environment variables in the shell when overriding values.
- **API base URL:** `tests/api.spec.js` uses `BFF_URL`, defaulting to `http://localhost:8090`. The browser `baseURL` is configured independently through `BASE_URL`, defaulting to `http://localhost:3001`.

## Runtime configuration and artifacts

`playwright.config.js` selects Chromium, sets the browser base URL and timeout values, and uses one worker to avoid conflicting mutable claim workflows. It enables retained traces, failure screenshots, and failure videos. The configured reporters include terminal output and a locally generated HTML report.

To run the tests:

```powershell
Set-Location qa-automation
npm ci
npx playwright install chromium
npm test
```

For deterministic single-worker execution:

```powershell
npx playwright test --workers=1 --retries=0
```

The HTML report can be opened with `npm run report`. Failure traces, screenshots, and videos are saved under `test-results/`; the HTML report is saved under `playwright-report/`.

## Boundaries and prerequisites

- Start the application first using the repository-level setup instructions in [README.md](../README.md).
- Browser tests require the UI, BFF, claims service, and a working local identity provider. The full stack is started with the root Docker Compose configuration.
- API tests target the BFF and depend on the configured BFF URL being reachable.
- The suite is an end-to-end QA layer, not a substitute for the React component tests, Java service tests, OpenAPI/AsyncAPI contracts, or database migrations.
- Keep application code, existing Playwright cases, and other folders independent of this architecture document; it describes their existing relationships without changing them.
